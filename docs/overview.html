AI Development Harness
十層剖面圖

一套讓 AI coding agent 可靠交付的分層系統。核心信念 —— 可靠性不來自 prompt 寫得多好,來自 repo 裡的結構化產物、包在外面的強制機制,與會自我改進的回饋迴路。

10 LAYERS 6 CLUSTERS ai-dev-harness ↗ harness-for-builders ↗

分享安全版:機制照「功能與設計」描述,不含帳號、密鑰、私人路徑。可轉移的那一層已抽成獨立框架 harness-for-builders。

00

為什麼要 harness

把開發交給 AI,會撞到一組測試蓋不到的失效點 —— 不是「程式對不對」,是「協作」的問題。這套系統就是逐一對應這五點建防線。

跨 session 失憶
agent 忘記上次做到哪,每次重新摸索整個 codebase
假完成
宣稱「做完了」但根本沒跑過驗證
範圍蔓延
擅自做清單外的事、改到不該碰的檔案
目標軟化
為了讓測試過,偷偷放寬驗收標準
走錯流程
套用另一套方法論,產物落到別的地方、繞過簽核關卡
Context 燒光
歷史雜訊塞爆脈絡,每次開場都變慢

L1

強制機制 Hooks

強制 · 系統核心

~/.claude/scripts/ + settings.json

  • 三種 hook 事件各司其職:SessionStart 管每次都要在場的東西,兩支 PreToolUse 一支管做了什麼(越權)、一支管有沒有照流程走,PostToolUse 管還能不能繼續
  • SessionStart 常駐入口 —— 把「按需知識庫」的入口注入每個 session。問題在於知識庫是權威(專案目標、過去決策、進行中的提醒都在那)但從不自動載入,而 rules/common/ 每次都在,於是權威那份形同不存在。寫在 CLAUDE.md 的條件式指示打不過無條件常駐注入:同機器上 persona 類 plugin(SessionStart 注入、語氣是 ACTIVE EVERY RESPONSE)每次生效,而 CLAUDE.md 裡「任務涉及 X 就讀 Y」實測不觸發。三個坑:① 判準要寫成看得到的觸發物,不是要判斷的類別(「使用者一講出專案名」可行,「任務涉及某專案的規劃」不可行);② 讀到不等於用到 —— 要補「讀完要做什麼」;③ 深指標鏈跳一半會停,壓平成平行讀,短內容(如身份設定)直接內嵌進注入文字
  • PreToolUse ① 越權 —— 攔在 Edit｜Write｜Bash 前 → DENY 改到凍結的 acceptance、改到已簽核 envelope 的 constraints 與 non_goals(比對陣列元素,追加放行、改寫或刪除擋下)、危險命令(rm -rf、git push --force、--no-verify);RECORD repo 外寫入、status 改 passing、用 Bash 改 feature_list.json → .harness/trace.jsonl。保護不綁工具型別:原本只認 Edit,改用 Write 或 Bash 寫同一個檔就整組失效。RECORD 的白名單:repo 外寫入有兩個例外不記 —— agent 自己的暫存命名空間,以及流程明文要求寫入的外部路徑(知識庫的專案資料夾:收工要在那裡留開發日誌與技術決策)。少了第二項會出事:規則叫 agent 寫、hook 記它越權,兩邊打架時帶警告的那邊贏,結果那個位置長期收不到紀錄,看起來像模型不聽話,其實是系統自相矛盾。白名單只開到該寫的那個子目錄,不擴大到整個外部空間
  • PreToolUse ② 流程 —— 攔在 Skill｜Read｜Edit｜Write｜Bash 前 → DENY 在 harness 專案裡呼叫另一套方法論的規劃 skill(它們的終點是計畫文件,而這裡的終點是經簽核、凍結進 feature_list.json 的驗收清單);RECORD 操作某專案的檔案卻不在該專案目錄內 —— 開場第 0 步沒做的訊號
  • PostToolUse 每個工具後 → 以每帳號用量為事實來源,額度逼近上限且在開發流程中時,指示寫交接、收工
  • schema-drift 機制自檢 —— hook 是 fail-open 的:上游改了 payload 契約就會無聲關閉,而 trace 照記 ok。缺必要欄位時改記 schema-drift 並示警
  • 這是「凍結 acceptance」從口號變成真牆的地方 —— hook 在執行前 DENY,AI 繞不過去;而一道會無聲倒塌的牆比沒有牆更危險,所以牆本身也要體檢

L4

Agent 角色

檢查

~/.claude/agents/ + 內建

  • 角色依用途分層,不是一條「少開 subagent」的通則 —— 分錯層的代價方向相反:檢查者多開一個是假獨立性,執行者少開一個是白燒主 session 的 context
  • 檢查者 —— acceptance-verifier(做對了沒)、plan-verifier(動工前只讀規格的冷讀)。同模型分身共享同一套誤讀,所以只跑一個,不為了多視角疊第二個;獨立性來自 fresh context 與唯讀的凍結輸入,回報不得寫成跨模型獨立驗收。工具收斂成白名單並停用委派
  • 執行者 —— 只有一支 executor(機械改動與有界技術判斷都歸它),釘 sonnet。目的不是獨立性是省額度:跑在獨立 context,主 session 只收最後一則訊息。不收安全敏感工作 —— 契約是「照規格做完」,而安全最需要的正是「規格本身有沒有漏洞」的判斷
  • direct-first —— 預設主 session 自己做。只有使用者明說要委派、兩條以上真正獨立可平行、或搜尋會吃掉大量 context 才派;實測完整編排的 token 與延遲大多落在主 session,不在便宜的 child
  • 探索者 —— Explore 覆寫內建版,釘死 haiku:內建版會繼承主 session 模型,等於用最貴的配置做最不需要判斷的全庫搜尋
  • 另用內建 Plan(架構設計)
  • 原則:生成者 ≠ 驗收者 —— 同脈絡的模型無法誠實評自己的產物;角色邊界靠 frontmatter 釘死,不靠規則叮嚀。省的是模型階層與 context 隔離,不是 effort —— 實測 97% 成本是長 session 重送 context、reasoning 只占 0.1%
L5

五階段生命週期與判決

檢查

rules/common/development-workflow.md

  • 五個階段一律經過:Discovery → Plan → Approval → Execution → Verification。檔位與階段垂直 —— 階段管順序,檔位管深度
  • 按風險分三個檔位:fast 只跑最小檢查 · default 改 passing 前做獨立驗收,有具體 code risk 才加 review · strict(安全邊界、不可逆操作、資料/schema/migration、發行)review 與驗收都跑並留 rollback 證據。檔案多、純 UI、對模型沒信心,單獨都不升級
  • Approval 是硬關卡:material work 先呈 Plan,等後續一輪明確核准才動原始碼 —— 一開始那句廣泛請求不算核准。大工作切 envelope + slice,envelope 簽核不等於底下都獲准,每輪只審下一個可執行的 slice
  • 判決分兩層:檢查者標 P0–P4 + Confidence,主 session 給 FIX/DEFER/REJECT,選項被 severity 夾住(P0 只能修、P1 不可延後),REJECT 必須有證據
  • 重驗有預算:預設一次;高風險 P1/P2 最多五輪,第 3 輪起是緊急恢復。重派前比對 git 狀態 hash —— 絕不重驗同一個狀態
  • 驗收鐵律:只餵凍結的 acceptance + 成品,不給開發過程,對照逐條檢查附證據
  • 這一層大多未經實測 —— 來自 pilotfish 的設計論證,本地唯一一次對照實測方向相反,所以帶 unproven 標記交給 Meta Loop 定期追問
  • 曾經有一層跨模型檢查者(Codex CLI),2026/08 移除 —— 論證沒錯,錯在漏寫前提「管道要穩定」。實際獨立性 = 理論值 × 可用率

03

設計原則

濃縮成五條可以拿去講的東西 —— 為什麼這樣設計會有效。

P1

可靠性來自產物

prompt 是易失記憶;檔案是持久、可版控、可審計的單一事實來源。新 agent 打開 repo 就該答得出「怎麼跑、做到哪、下一步、算不算完」。

P2

分層防禦

每個失效點對應一層防線:失憶→交接檔、假完成→evidence 閘門、範圍蔓延→邊界規則、目標軟化→凍結 acceptance + hook DENY。

P3

規則要有牙齒

「請遵守」對有最佳化壓力的 agent 沒用。關鍵約束由 PreToolUse hook 在執行前強制,不是靠自律。

P4

生成與驗收分離

生成的模型會偏袒自己的產物,驗收交給脈絡乾淨的另一個 session,只餵凍結的 acceptance + 成品。

P5

系統會自我改進

trace + failures 餵進 Meta Loop,用實際數據做消融檢討,避免 harness 自己變成 cargo-cult。

04

演進與教訓

踩過的坑 —— 這些通常比「我做了什麼」更值得在面試裡講。

凍結≠不會錯
曾遇到驗收 fail 其實是「凍結的規格把既有現狀描述錯了」(規格 bug,不是實作 bug)。回簽核改規格,不硬改實作。凍結的是「目標」,不是「不會錯」。
獨立性會被基礎設施悄悄破壞
代理接管模式開啟時,以為在跑另一個模型,實際跑的是同源模型,review 失去獨立性。凡是宣稱「獨立」的檢查先確認路由;做不到就如實寫成同模型 fresh context。
消融檢討防 cargo-cult
每個組件都有維護成本。收官時用 trace 數據問「這層真的擋住問題了嗎」,沒發揮作用的下個專案不照抄。小專案停在 L1 是正確的。
檔案瘦身 = context 預算
分「每 session 都讀的操作檔(保持精瘦)」vs「收官才讀的檔案庫(不縮)」,避免歷史雜訊塞爆 context。
防線會無聲失效,所以防線本身要被監測
hook 是 fail-open 設計:欄位讀不到就靜默放行。上游改一次 payload 契約,整道防線關閉而 trace 照記 ok,看起來比平常還健康。回歸測試只在「我改動它」時跑,擋不住「它自己壞掉」。
規則寫在文件是宣示,寫在 capability 才是機制
檢查自己的規範時要問「這條靠什麼執行」;答案若是「靠模型記得」,那就等於沒有。能釘進 frontmatter、白名單、hook 的,就不要只寫進文件。
保護綁工具型別 = 換個工具就繞過
凍結 acceptance 的 DENY 原本判斷「這是不是 Edit 操作」,結果用 Write 整檔覆寫或用 Bash 改同一份 JSON,兩條保護都靜默失效。保護要綁在被保護的對象上,不是綁在到達它的路徑上。反面同樣真:過嚴的 DENY 會把人逼去用沒有保護的繞道。
兩套方法論的岔路
通用 agent 方法論與自己的 harness 前半段高度重疊(都從釐清需求開始),尾巴卻不同:一個終點是計畫文件,一個是經簽核凍結的驗收清單。重疊讓人以為可以互換,於是簽核關卡被整段跳過。而注入式的流程提示位階高過自己的設定檔 —— 光在規則裡多寫一段會被蓋過去,得靠 hook 才擋得住。
一條規則的效力,只到它的論證涵蓋得到的地方
「不新增自訂 agent」原本的理由是「同模型分身共享同一套誤讀」—— 那句話只對檢查者成立,卻被整段套到執行者與探索者身上,於是最不需要判斷的全庫搜尋一直跑在最貴的模型上。同期還有另一半誤判:憑感覺以為「壓低 effort 就會省」,實測歸因後才發現 97% 成本是長 session 重送 context、reasoning 只占 0.1%。規則要跟著論證走,成本要跟著量測走。
測資自己捏 = 測試全綠但真實輸入全掛
新 hook 通過 15 個自製情境,換成真實格式的輸入卻全部靜默失效;真因是自製測資本身寫錯(路徑跳脫),而 fail-open 讓它看起來「什麼事都沒發生」。合成測資只驗得到自己想像中的形狀。
