Harness 五階段作業圖

這是 系統剖面圖的另一半：剖面講「有哪些層」，這頁講「一件事進來怎麼走」。五個階段一律經過，檔位只改每階段的深度，不改要不要走。圖裡的紅色是硬關卡——不是提醒，是停下來。

主流程 ／ 一件事從進來到收尾

Approval ／ 唯一的硬關卡

material work → 呈 Plan → 停

「使用者一開始那句廣泛的請求」不算核准。對一份他還沒看過的 Plan，原始請求構不成同意。停下來的形式就是呈 Plan 並結束該輪，不需要一個按鈕。

核准前可以做唯讀釐清，不可以做任何來源變更。低風險、可逆、局部的工作不是 material work——階段照走，關卡不觸發。

檔位 ／ 決定每階段多深，不決定跳過哪階段

檔位什麼時候做到哪
fast 低風險、可逆、局部，沒有正式 feature 直接做，跑最小檢查，不自動 review／verify
default 一般功能與 bugfix frozen acceptance ＋最小回歸檢查；正式 feature 轉 passing 前派 acceptance-verifier
strict 安全與信任邊界、不可逆操作、資料／schema／migration、發行、跨元件關鍵流程 再加 /code-review 與 rollback 證據

升檔的判準是失敗後果與可逆性。檔案多、例行文件、純 UI、或「對模型沒信心」本身都不升級。

派不派 ／ 預設是不派

條件成立才委派（三者任一）
明說使用者說了「委派／交給 executor／派給 subagent」
真平行兩條以上真正獨立、檔案不重疊，而且主線還有事可做
省 context搜尋或批次工作會吃掉大量 context，且輸入與停止條件完整

留在主 session 的：未知 bug 的診斷、需求／架構／整合取捨、最終決策、以及 authn／authz、密鑰、隱私、加密、輸入驗證這些安全面。寫入型派工缺任一要件就不派——目標、限制、done criteria、路徑、原因。

派出去之後，同一輪就排保溫鬧鐘（ScheduleWakeup 2700s，＝ 60 分 TTL × 0.75）。鬧鐘會自我取消，所以不必先估這次要跑多久。

檢查結果 ／ 兩層：檢查者標 severity，主 session 給處置

Hook ／ 唯一真的有執行力的那層

時機腳本做什麼
Agentdelegation-warmup派 executor 沒設 worktree 直接 deny；其餘注入保溫提醒
Edit｜Write｜Bashharness-trace記 trace、擋 destructive 指令與凍結 acceptance 的改動
Skill｜Read｜Write…harness-gate擋掉與 harness 規格終點競爭的流程
Write｜Editno-emoji-guard擋寫進檔案的 emoji
每次工具呼叫usage-guard額度接近上限時提醒收工

規則寫在文件裡靠模型記得，對話一長就沉底；hook 出現在做決定的那一刻。能寫進 hook 就不要只寫進文件——這也是為什麼圖上只有 Execution 那格的 worktree 是真的擋得住，Approval 那格擋不住。
